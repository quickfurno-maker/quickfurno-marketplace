- **20.3A1R Assignment lineage idempotency correction** — `COMPLETE`. **Documentation only** — no database access (production **or** staging), no SQL, no migration, no runtime change, no deploy. Removes a **design defect**: the 20.3A/20.0 drafts made `lead_assignment_events` idempotent through **`UNIQUE (lead_id, vendor_id)`** and seeded it with `ON CONFLICT (lead_id, vendor_id) DO NOTHING`, which is incompatible with an append-only lifecycle event stream — a single (lead, vendor) pair must record many events (`assigned → delivered → accepted → completed`, or `rejected`/`invalid`/`replaced`), and the constraint would silently discard every event after the first. **Corrected model:** `event_idempotency_key text NOT NULL` with `UNIQUE (event_idempotency_key)` as the table's **only** unique constraint; seed key `legacy_assignment_seed_v1:<assignment_id>`; runtime key `assignment_event:<operation_id>:<assignment_id>:<event_type>` (+ ordinal where one operation legitimately emits repeats), always derived by the **authoritative transaction**, never by a caller. **Lifetime is a query, not a constraint** — `COUNT(DISTINCT vendor_id)` over `event_type='assignment_created' AND lifecycle_to='assigned'`; later events and failed candidates consume no slot. Idempotency boundaries are now **four and separate** (operations · assignment rows · ledger · events) and may not be merged. The existing `lead_assignments UNIQUE(lead_id, vendor_id)` is **unchanged**.
