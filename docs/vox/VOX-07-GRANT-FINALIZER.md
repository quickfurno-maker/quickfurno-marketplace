# VOX-07 — reviewed, city-checked atomic staff grant finalizer

**Source-only milestone.** The new `20261014030000_vox_v1_approved_grant_finalizer.sql` migration depends on both prior unpublished VOX-03/05 migrations. It creates the immutable `vox_staff_access_activations_v1` table and the **service-role-only** finalizer `qf_vox_activate_reviewed_access_v1`. That PostgreSQL transaction checks the same **reviewer** was an active Superadmin and was distinct from requestor and staff target, the decision is exactly APPROVED with matching independent review receipt, the request is nonexpired, city/team/target active, no existing grant, and requested role permits the exact object family. It uses authoritative Core city relations for prospect/vendor/support_thread/prospect-or-vendor conversation scopes, not browser locality.

The mutation, audited activation receipt and immutable staff grant audit event commit in **one transaction**. Replays, stale/out-of-city/unknown objects, mismatched finalizer, duplicate membership and overlong grant windows are rejected. Neither this schema nor the next HTTP route contains Meta, vendor state, wallet, matching or cross-agent send capability.

The Core route `POST /api/vox/v1/staff-grants` exists ONLY as source. **OFF by default:** requires `VOX_STAFF_GRANTS_ENABLED=staging`; verifies independent remote Supabase Auth `getUser` and AAL2 via the existing owner bearer helper, plus Core active `profiles` and trusted `app_metadata.admin_role=Superadmin`. The route derives `requested_by`, reviewer and finalizer from that verified owner; never trusts a client-supplied actor. Three actions are request (no grant), review (atomic receipt, no grant), activate (fully reviewed atomic grant). All account and object IDs are validated as bounded UUIDs; no direct service-role credentials in browser or generic CORS. No staff web write UI is provided until isolated staging security tests are certified. A real release MUST include origin, credential/audit/redaction/rate controls in front of the endpoint.

**Disposable PostgreSQL proof** in network-disabled local Postgres 16: all three migrations and synthetic user/city/prospect fixtures applied. One valid reviewed membership and same-city prospect grant activated; 2 audit/activation receipts; replay, wrong-city scope, unreviewed and wrong reviewer denied. No real Staging migration.

**Emergency revocation extension (source-only):** A separate service-role-only `qf_vox_emergency_revoke_staff_v1` allows an authenticated existing Core Superadmin to immediately and atomically set staff membership inactive, revoke all active object grants, and append a uniquely identified `STAFF_REVOKE` audit incident. Team-ID equality guards against wrong-target selection, actor cannot revoke themself, replay and non-Superadmin callers fail. This is a narrow incident-containment exception to normal prior approvals; it cannot issue privileges. Offline PostgreSQL test proves membership and all scopes revoked and audit now 3 entries (2 grants + 1 revoke).
