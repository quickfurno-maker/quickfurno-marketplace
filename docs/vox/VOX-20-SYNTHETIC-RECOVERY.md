# VOX-20 Isolated Disaster Recovery — synthetic PG17, not managed Staging

This test creates two **network-isolated disposable PostgreSQL 17 containers** on the authorized runner. It builds a source DB with the existing synthetic native/Core/Aarohi dependency fixture, applies the **seven unchanged pinned VOX migration SQL files**, inserts only synthetic profile/city rows, and produces a custom-format `pg_dump` inside the source container. It copies out the binary archive, verifies SHA-256, restores it in a second isolated container with deliberately reconstructed synthetic Postgres roles and preserved grants, checks equality of table counts, rows, all VOX row-level security with FORCE enabled, denied anon/authenticated grants, denied privileged function execution and a genuine failed `SET ROLE anon` SELECT. All containers and temporary archive are cleaned in `finally`.

No real vendor/PII/Auth backup, Supabase secrets, service-role keys, customer data, provider messages, or managed Staging changes are made. **This is NOT verification of the real Supabase project's Pro backup retention, complete Supabase Auth/Storage backups, managed PostgreSQL roles, extensions, cron, recovery objective, and real separated restore capability.** Production and managed Staging remain RELEASE HOLD: the same full live backup + checksum + independently restorable isolated target + current 86-migration parity + owner-reviewed seven SQL apply and signed private E2E are still mandatory.
