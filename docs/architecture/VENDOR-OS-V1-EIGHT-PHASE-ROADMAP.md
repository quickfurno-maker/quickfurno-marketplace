# QuickFurno Vendor OS V1 — Final Eight-Phase Roadmap
Date: 12 October 2026 IST
Status: PROPOSED; Phase 01 trace canvas has an implementation candidate in feature worktree, not deployed.
Namespace: VO-01–VO-08. Does not overwrite AGNI or platform-scale phase numbering.

## 0. Verified baseline and architecture
Observed in QuickFurno production tables: 28 vendor records, 14 approved, 8 linked dashboard accounts, zero verified office locations; 71 lead assignments, 81 vendor credit logs, zero vendor CRM profiles, zero package orders or payments; 83 automation jobs, seven client successes and zero successful vendor jobs; 16 communication catalog items operationally disabled; 11 conversations with zero ANISHA assignment; one recorded AOS run. Native automation worker is heartbeating but has no recorded processed jobs. External Meta and Razorpay status and actual VPS deployment revision remain independently unverified. These counts are evidence of records, not a statement of actual customer volume.

Permanent boundaries: Core owns identity, eligibility, consent, money, lead matching and exactly one debit per authorized assignment. Maximum three vendors per lead. There is NO per-lead accept/reject workflow. Jarvis/Anisha advise and converse; AOS observes/recommends; Core authorizes; Native Automation executes; providers deliver; AGNI observes and governs. Trial eligibility follows Core policy, not assumed paid-only rules. Never clone Core truth into a second authoritative CRM.

## Foundation: use existing Automation Studio / Workshop
Reuse six visual lanes already implemented: client_journey, vendor_journey, campaigns, recovery, orphan_cleanup, stale_cleanup. Reuse native worker, durable job/attempt ledgers and Core vendor action registry. Active vendor action contract: vendor.lead_offer (one-way assignment notice), vendor.response_reminder (2h/24h when status New), vendor.onboarding_reminder (24h after CRM creation), vendor.package_expiry_warning (7d/1d before expiry), vendor.low_credit_warning (threshold crossing). Registered vendor.document_reminder is intentionally non-producible because there is no authoritative vendor-document lifecycle. Never present it as enabled.

Workshop is a CONTROL AND VISUALIZATION plane, not a second execution engine. Editable nodes cannot modify assignment cap, credit rules, recipient identity, secrets, arbitrary endpoints or Core approval. A published graph/version must be truthfully labeled: until graph-to-runtime binding is independently certified, the diagram is advisory/visual and the coded native worker remains execution authority. Ensure n8n/Temporal/native workers cannot accidentally own the same exact action.

Trace Canvas has TWO modes: Design + Simulate (editable draft; no side effect) and Trace + Observe (read-only persisted business events; unknown/stale shown explicitly). Every viewed step must link to source authority/evidence, not a generated narrative. Search vendor, lead, assignment, job and correlation ID; filter by failed/uncertain/late; show event time, processing time, authority, safe reason code, idempotency, retry, definitive provider outcome and recovery owner. Highlight the matching visual action but never imply the current draft was the exact historic executable graph. Allow owner to copy a sanitized investigation reference.

Event envelope (map existing schemas, do not invent conflicting events): event_id, schema_version, occurred_at, observed_at, producer, subject_ref, correlation_id, causation_id, vendor_ref, lead_ref, assignment_ref, action_request_ref, job_ref, attempt_ref, outcome, safe_code, evidence_ref, policy_version, provider_certainty. Redact phone, message contents, model prompts, OTP, secrets. Queue, worker, provider, Anisha, AOS and AGNI emit bounded interoperable links. Telemetry must not block live business operations.

## VO-01 — Forensic audit, canonical state machine and trace foundation
**Goal:** stop guessing which vendor stages and flows actually work.
**Reuse:** Core tables/RPCs, services, automation ledgers, existing Studio, Agent Flow Canvas, telemetry.
**Tasks:** audit exact deployed revisions vs main, migrations, runtime flags, all vendor states; classify REUSE/FIX/CONNECT/EXTEND/NEW/RETIRE; reconcile assignments with every wallet log reference and historical correction (do not falsely claim that unmatched reference means money lost). Establish a derived, evidence-backed state machine from acquisition -> submitted -> verified -> approved -> dashboard linked -> geo complete -> package/trial ready -> eligible -> assigned -> notification -> engaged -> recharged/paused/win-back. Track explicit blocker, authority, next action and terminal state. Audit source producer -> action request -> Core decision -> job -> attempt -> transport -> provider receipt. Add read-only superadmin Studio trace by exact job UUID, historic execution lookup, safe codes and evidence timeline. Adopt stable cross-service correlation.
**Failure drills:** duplicate event, missing vendor account, expired package, unknown provider receipt, historical job replay attempt, inconsistent wallet references, absent source telemetry.
**Exit gate:** every existing cohort accounted for; source commit/DB snapshot captured, unverified claims labeled; trace API never mutates or exposes PII, no external delivery claim without receipt, one-click inspect Core/worker failures; typecheck, guard tests and audit signed. **Status:** worktree trace prototype implemented, not deployed or certified end-to-end.

## VO-02 — Vendor acquisition, registration and account activation
**Goal:** every vendor has deterministic eligibility and an explainable blocker.
**Tasks:** verify Aarohi -> registered vendor -> Anisha handoff, duplicate business/phone detection, anti-spoof identity, registration abandonment recovery, city/category/office Google Places, service zone and geo validation, admin approval/rejection, suspension and dashboard account provisioning. Resolve approved-without-login cases. Introduce idempotent CRM profile projection after canonical vendor existence; backfill only after dry-run and review. Avoid designing a document reminder without a document domain. Build account recovery and exact user/vendor RBAC.
**Workshop events:** registered, profile incomplete, location pending/verified, submitted, approved, login linked, handoff offered/completed/rejected, onboarding reminder eligible/suppressed.
**Tests/gates:** duplicate form twice -> one vendor; wrong number or unapproved city blocked; approved vendor can log in; false role never receives Anisha access; audit all production blocked states before migration; staging onboarding fully traced with no production sends.
**Dependencies:** VO-01 event and identity map. Parallelizable with VO-03.

## VO-03 — Packages, Razorpay, credits and commercial integrity
**Goal:** one captured authorized order = at most one package activation and exact credit ledger.
**Tasks:** audit existing Razorpay checkout/signature/webhook and package services, price snapshot, currency, payment capture vs paid flags, trial and expiry policy, recharge purchase, declined/canceled/uncertain outcomes, refund with approval, admin grants, atomic wallet RPC and assignment debit. Reconcile historical logs against assignment operations including correction entries; no blind mass repair. Build exact order/payment/activation state machine and idempotent provider webhook replay reconciliation. Investigate empty package/order/payment cohort without seeding fake production sales.
**Workshop events:** order created, payment confirmed/uncertain, package activated, credits granted, threshold crossed, recharge reminder, package expiring, adjustment approved.
**Tests/gates:** 10 duplicate webhooks, concurrent recharge, crash between captured and wallet grant, bad signature, wrong amount/currency, refund replay, negative balance, trial eligibility. Staging end-to-end order -> verified capture -> exactly-once credit; Core and AGNI expose precise financial evidence.
**Dependencies:** VO-01 ledger audit; VO-02 vendor identity. Razorpay live credential setup reserved for VO-08.

## VO-04 — Matching, lead notification and measurable vendor value
**Goal:** eligible vendors actually see and can progress relevant leads without fairness/credit drift.
**Tasks:** reuse fair-turn/distance band matching, service-zone eligibility, active credit policy, per-lead max-three assignment, atomic debit, dashboard lead visibility, lead status progression, bad-lead complaints and governed credit restoration. Audit location backfill, fairness over time and assignment records not projected to latest delivery. Standardize dashboard_queued, dashboard_visible, WhatsApp_preview, provider_accepted, provider_sent, delivered, read, failed, unknown; never treat preview or accepted as delivered. Connect real provider receipts where certified; catch dead-letter and unknown outcomes. Instrument lead usefulness via vendor follow-up and complaint outcome, not lead acceptance.
**Workshop events:** lead eligible -> matching -> assigned -> debited -> dashboard visible -> notification requested -> template variables resolved -> provider outcome -> reminder scheduled/suppressed.
**Tests/gates:** same-lead ten-way gives max three, concurrency charges exactly once, no notification after vendor loses entitlement, no reminder when vendor status progresses, replay safe, complaint refund idempotent; evidence links across Core/queue/delivery.
**Dependencies:** VO-02 + VO-03. Provider live canaries deferred until VO-08.

## VO-05 — Anisha agent, inbox and real relationship workflows
**Goal:** authorized vendor can ask Anisha for help across full lifecycle.
**Tasks:** reuse role-bounded Anisha intent engine, Jarvis prompt orchestration, WhatsApp identity resolver and Core conversational outbox. Fix zero live Anisha conversation evidence by verifying provider/routing gates, phone matching, actor ownership, live Core facts, response window, consent, human takeover and AI pause. Build guided onboarding, lead response education, recharge explanations, complaint intake, support ticket/task, multilingual Hindi/English/Hinglish, continuity and appropriate human escalation. Optimize simple replies with deterministic FAQ/low-cost route and stronger models only when needed. NO independent balance mutation, payment, assignment or per-lead accept/reject.
**Workshop + Jarvis Canvas:** trace inbound receipt -> verified vendor -> role guard -> intent -> context -> model/FAQ -> proposed reply -> Core consent/approval -> outbox -> provider receipt -> human escalation. Do not duplicate the Jarvis flow editor.
**Tests/gates:** 30+ realistic multi-turn test cases with wrong role, stale balance, privacy attack, unsupported request, complaint, billing ambiguity, WhatsApp retry and handover; first real staging vendor conversation externally certified only when Meta test number ready.
**Dependencies:** identity VO-02 and Core facts VO-03/04; work may proceed alongside VO-04.

## VO-06 — Repair native automation; event canvas fully correlated
**Goal:** all existing vendor actions work reliably without a second worker or silent failures.
**Tasks:** diagnose historical QF_EXEC_VARIABLES_UNRESOLVED (14 failed vendor jobs) and expired backlog (40 vendor cancellations), template-variable builders, catalog vs enabled state, metadata, worker claim, runtime version drift, missing trigger producers, consent, suppression, template mapping and Meta acknowledgement. Reconcile native/Temporal/n8n ownership one action at a time; keep obsolete paths dormant or retire after proof. Wire action-specific events to the Studio timeline and trace provider results using exact message linkage, with UNKNOWN on ambiguous timeout. Implement search, time range, stale/unknown badges, click node -> event evidence, status map, safe-code explanations, incident link, version mapping, preview-only simulation, governed publish/rollback and allowlisted retries. Expose real success rate separately from worker heartbeat/cycle count.
**Tests/gates:** each of the five authorized vendor flows has passing happy path, failure path and suppression path in staging; ten duplicate triggers cause one authorized effect; crash/retry, lost receipt, expired window, wrong variable mapping, template approval missing, human stop and consent revocation never cause duplicate sends; identify any action with no honest producer rather than fabricating trigger.
**Dependencies:** VO-01 core trace, producer truth from VO-02/03/04, Anisha events VO-05. Start failure repairs immediately, not sequentially at Phase 06.

## VO-07 — AOS vendor success, proactive Anisha and AGNI
**Goal:** improve vendor experience, retention and fairness with evidence-based intelligence.
**Tasks:** connect existing AOS vendor-success projections for low package readiness, inactive 30 days, matching demand, complaint, recharge opportunity and retention risk; do not duplicate matching/rescoring. Derive vendor health from activation, lead relevance, contact progress, complaint/refund outcomes, responsible recharge and inactivity with explicit confidence and freshness. Start in preview/advisory mode. Feed AOS suggestions -> Core validation -> optional human approval -> Core-owned automation -> measured outcome. Integrate operational CRM tasks/notes/segments only when populated, no second authoritative money state. AGNI dashboard must show vendor journey timeline, Anisha handovers, AOS recommendations, retry queue debt, fairness and risk, provider delivery certainty, drift, and owner-safe approval controls.
**Tests/gates:** stale or incomplete signal cannot authorize a send; AOS cannot debit, assign or expose private contact; approval fingerprint single-use; cross-vendor isolation; bounded AI cost; real staging recommendation and measured follow-up linked via correlation; no unsupported 'self-learning' from raw conversations.
**Dependencies:** VO-04 outcome events, VO-05 dialogue and VO-06 automation evidence. Signal development may run in parallel early.

## VO-08 — Internal certification, external activation, production rollout
**Goal:** production-grade E2E closure without misleading green labels.
**Tasks:** certify migration order, staging restore, signed release, feature flags, per-lane stop, rollback, worker/failover, observability, security, consent, retention, latency and cost budgets. Run synthetic vendor from acquisition to reactivation and all negative branches. External dependencies last: Meta WhatsApp number/WABA/templates/permissions, Razorpay live account and webhook, any verification providers. Canary with opted-in test vendors, then limited real cohort and measured ramp. Green gates require source evidence for every assigned/debited/delivered message, UNKNOWN for missing provider proof and owner-visible incidents for failures. Preserve fail closed.
**Tests/gates:** zero duplicate financial effects and >3 violations in concurrent/replay scenarios, zero unauthorized communications, agreed p95/SLO targets from measured staging baseline, E2E traced for happy + negative paths, external provider ACK receipts and correct handover, rollback drill and owner signoff before expansion.
**Dependencies:** all preceding certified phases; perform internal mock/provider-contract testing well before last phase.

## Delivery order, ownership and exit evidence
Critical path: VO-01 -> VO-02 + VO-03 in parallel -> VO-04; VO-05 + VO-06 in parallel once identity and event truth exist -> VO-07 -> VO-08. AOS preview and AGNI read-only can start early. Every phase outputs exact SHA/PR/migration, decision matrix, test IDs and results, staging trace, risk register, rollback, performance + token budget, internal/external dependencies, and Notion memory update. Phase completion requires deployed/staging/runtime evidence as specified, not just code or CI.
