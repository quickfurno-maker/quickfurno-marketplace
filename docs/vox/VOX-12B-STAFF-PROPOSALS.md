# VOX-12B — Staff-originated governed operational proposals

Source-only, **default disabled** until signed private Staging. The existing Core `action-intents` API (#221) can now be invoked from the staff VOX acquisition, Vendor 360 and Service Desk screens, each using one shared `StaffProposalForm` client component and same-origin `POST /api/propose-action` BFF. It reuses the canonical Aarohi/CRM/Service Desk read models to display **only previously Core-scoped records**, excluding do-not-contact prospects. No second CRM, ticket store, grant system, or direct WhatsApp gateway is created.

The browser may submit only registered action kind, assigned target UUID, retry-safe UUID nonce and matching fixed reason code. **No free-text, personal information, actual message, profile payload, or agent reasoning** is sent from this form. The BFF enforces same-origin, bounded JSON and allowlisted fields; the server revalidates Supabase AAL2, required `VOX_STAFF_PORTAL_ENABLED=staging`, `VOX_STAFF_VIEW_MODE=scoped`, distinct `VOX_OPERATIONAL_PROPOSAL_UI_ENABLED=staging`, pinned HTTPS Staging Core, and obtains the Core bearer only from server-side session. Core independently validates current exact staff role/team/city/prospect/vendor/thread grants, canonical subject location and request nonce. A valid proposal yields `PENDING` and `NOT_AUTHORIZED`, not a mutation of the target.

Owner review of such proposals lives at `/approvals` and the **only currently implemented reviewed business executor** is the native internal Aarohi FOLLOW_UP task #224 (separately flagged OFF). Support reply, vendor profile change and all Meta/provider actions are not executed by the proposal route. Real UI↔Core Staging positive/negative IAM tests, no-cross-city/IDOR, concurrency, audit, signed rollout and rollback still required. **No real account or data altered.**
