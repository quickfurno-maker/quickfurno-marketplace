# VOX-12C — Optional dual-mode VOX browser bridge (default remains disabled)

Before this change VOX had an application-process global `VOX_STAFF_VIEW_MODE=owner` OR `scoped`, preventing one deployment from presenting owner and scoped staff together even though Core has independent AAL2 authorization. New **explicit opt-in** `VOX_STAFF_VIEW_MODE=dual` permits both source UIs without granting either role from environment variables. Actual access for every API remains determined solely by fresh server-verified Supabase MFA and canonical Core endpoint owner/individual team/city/object-grant checks. No browser receives Core bearer or service-role credentials.

Overview: for dual mode only, invoke owner Core `/api/vox/v1/overview` first, and fall back to scoped Core `/api/vox/v1/my-work` **only on HTTP403**. Never fallback on Core 401, 5xx or malformed response. Owner-only methods continue to call their owner-only Core endpoints; scoped methods continue to call Core scope-specific endpoints. No automatic membership, staff role elevation, broadened Core grants, financial or provider actions are introduced. Default disabled portal and individual feature gates unchanged.

**Important**: dual mode is *source code only*; owner and scoped users have not been simultaneously verified with real Staging AAL2 sessions, nor unauthorized cross-role negative HTTP tests. Real mixed-role production access MUST NOT be activated until these checks, the private origin, WAF/rate limiting and leak tests are certified. This is UX infrastructure, not evidence of full VOX readiness.
