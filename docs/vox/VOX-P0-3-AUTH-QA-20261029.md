## Why this exists

The 02c harness proves the route's control flow is correct against a **fixture** Supabase client and a **hand-crafted, unsigned** JWT. It cannot prove that the real `verifySupabaseBearerUser()` → `@supabase/supabase-js auth.getUser(token)` call actually performs real HTTP signature verification against a real Auth server, and it cannot prove anything about AAL2 because it has to fabricate the `aal2` claim itself.

This harness closes that gap **locally and disposably**: it reuses the same proven-in-CI pattern as `scripts/mvp/automation/certify-vl01-real-auth-http.mjs` (ephemeral Docker, loopback-only, synthetic generated secrets, pinned official images, no persistent state) to stand up a real GoTrue instance, then drives the real route code against it.

## What is genuinely proven (when the harness is run and passes)

- The real `lib/supabase.ts verifySupabaseBearerUser()` calling the real `@supabase/supabase-js` `auth.getUser(token)`, which makes a real HTTP request to a real (local, disposable) GoTrue `/user` endpoint and verifies the token's HS256 signature.
- A correctly-shaped-but-wrongly-signed token is rejected by real GoTrue signature verification (not just the route's own regex).
- A real GoTrue signup issuing a real signed `aal1` access_token, which the real route denies even when the Owner's `profiles` row and `app_metadata.admin_role` are both already correct — i.e., the AAL2 gate itself is real, not assumed.
- (Optional, see below) A real local GoTrue **TOTP MFA enroll → challenge → verify** cycle, using a code computed independently from the secret GoTrue issued (RFC 6238, `fixtures/totp.mjs`), producing a session GoTrue itself marks `aal2` — never a hand-signed or promoted claim. If that session's token is accepted by the real route, admission at HTTP 200 with the exact `qf.vox.overview.v1` projection is genuinely exercised end-to-end against a real (local) Auth + PostgREST + Postgres stack.
- (Optional) A real wall-clock-expired token (minted by a second, short-lived local GoTrue instance with `GOTRUE_JWT_EXP=2`, after a real 3-second wait) is denied.
- (Optional) A token for a user that was really deleted via the real GoTrue admin API is denied.

## What is explicitly NOT proven, ever, by this harness

- **Nothing about live Supabase Staging or Production.** This never touches a managed project; it hard-fails on startup if `SUPABASE_URL`, `DATABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` are present in the shell, or if `NEXT_PUBLIC_SUPABASE_URL` already points at a `*.supabase.co`/`*.supabase.in` host.
- **Nothing about a real human Owner's enrolled authenticator app or a real AAL2 session on Staging/Production.** PR #419/#421 Owner TOTP enrollment status on live infra is unchanged by this work and is not re-verified here.
- **Nothing about PR #422, P0-4, or the live VPS deploy path.** This is a standalone, non-deploy, code-only test suite.
- **Does not certify a signed release image.** No image is built, signed, or published by this harness.

## The AAL2-positive case may legitimately come back BLOCKED

The harness attempts the real local GoTrue MFA enroll/challenge/verify flow, but the exact factor-enrollment env toggle and endpoint availability on the pinned `supabase/gotrue:v2.196.0` image were not re-verified against a live container in this session (see **Execution limits**, below). The harness is written so that if any step of the MFA flow returns a non-success HTTP status or an unexpected response shape, it prints:

```
BLOCKED real route: genuine local-GoTrue TOTP MFA enroll+challenge+verify yields AAL2... :: <reason>
```

and continues — it does **not** fabricate a 200 pass, and a BLOCKED optional case does **not** fail the overall script (exit code stays 0) as long as every mandatory negative (anonymous, malformed/wrong-signature, AAL1-denied, POST/PUT/DELETE 405) passes. The same BLOCKED-not-faked contract applies to the expired-token and revoked-user cases.

**If you see BLOCKED on the MFA case**, the next step is to inspect the printed reason (HTTP status / response body excerpt) and, if it is an endpoint-naming or config mismatch, adjust `GOTRUE_MFA_ENABLED` or the `/auth/v1/factors...` paths in the harness against that GoTrue version's actual API — not to hand-sign an `aal2` claim to force a pass.

## Execution limits for this Claude session (why this was not run here)

This session's task scope explicitly disallowed Bash/PowerShell/terminal/Docker/network access and instructed the operator to validate independently. **This harness has not been executed in this session.** It was written by close structural analogy to `certify-vl01-real-auth-http.mjs`, which is already proven to run in CI (`.github/workflows/vl01-real-auth-http.yml`), reusing its exact container-lifecycle, port-discovery, and reverse-proxy code verbatim where applicable. The new parts — the VOX table schema, the TOTP helper, the MFA enroll/challenge/verify calls, the short-lived expiry instance, and the admin-delete call — are novel and have **not** been run end-to-end. Treat first execution as a real test run, not a formality.

## Operator execution

Prerequisites: Docker available locally and reachable from this shell; no `SUPABASE_URL` / `DATABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` set in the shell; no other process already using the ports (the harness only ever requests ephemeral host ports bound to `127.0.0.1`).

```bash
npm ci
node --disable-warning=MODULE_TYPELESS_PACKAGE_JSON scripts/mvp/vox/validate-vox-03-real-local-gotrue-auth.harness.mjs
```

### How to interpret the output

- `VOX_P0_3_GOTRUE_POSTGREST_PG_READY` — the disposable stack booted.
- A line per check: `PASS <name>` (asserted and verified), or `BLOCKED <name> :: <reason>` (optional case, infra/endpoint not available locally, not a fake pass).
- Final line `VOX_03_REAL_LOCAL_GOTRUE_OWNER_AUTH_PASS <n> passed, <m> blocked (not faked), 0 failed` and exit code 0 means: every **mandatory** real-auth negative passed, and every optional case either passed for real or was explicitly BLOCKED (never faked).
- `VOX_03_REAL_LOCAL_GOTRUE_OWNER_AUTH_FAILURE <message>` and a non-zero exit code means a **mandatory** check failed, or an optional case's infra came up but the route's behavior itself was wrong (e.g., an expired or deleted-user token was still accepted) — that is a real finding, not an infra gap, and must be treated as a release blocker.
- `VOX_03_REAL_LOCAL_GOTRUE_FIXTURES_CLEANED` always prints last; containers/network are removed in `finally` even on failure. If a container is ever left behind after an interrupted run (e.g., the process was killed), it will be named `vox03-gotrue-*-<pid>` — safe to `docker rm -f` manually.

Please record: the full console output (all PASS/BLOCKED lines plus the final summary line) and the exit code. If the MFA case is BLOCKED, record the exact reason string.
