## Problem resolved in source
08L's in-app Staff notification inbox was built, but no mechanism generated notifications from successful Core work transitions. 08N adds a transactional event-to-job bridge and a bounded Core-only processor. It does **not** configure a running scheduler or activate Staging/prod.

**Source-only candidate SQL:** `ops/vox/sql-candidates/20261016040000_vox08n_transactional_work_notification_outbox_candidate.sql`, exclusively OUTSIDE `supabase/migrations`. It creates one FORCED-RLS outbox table and an AFTER INSERT trigger on the existing immutable Core `vox_work_events_candidate_v1`; an accepted Core event and its outbox intent commit atomically. Unknown provider/event kinds abort the original transaction, rather than silently losing an outbox record. No new messages, direct client/vendor writes or notification-event fabrication.

Worker RPCs are `qf_vox_staff_notification_outbox_claim_v1`, `...process_v1` and `...fail_v1`, restricted to `service_role`. Claims use `FOR UPDATE SKIP LOCKED`, at most 10 jobs, 30–300s lease, fresh unforgeable per-claim token, max five attempts. A crashed 5th-attempt lease is dead-lettered. Processing a job re-reads the original durable work event and current team/city, and scans at most 100 team-members. It reuses 08L's full **neutral Staff / independent current department approval / unrevoked object grant / canonical city / dual vendor-support grant** helper immediately before calling the idempotent `qf_vox_staff_notification_enqueue_v1`. All eligible recipient inserts and DONE state occur in one PostgreSQL transaction, without external transport. Otherwise rollback/retry with capped exponential backoff and generic non-PII error code, then final dead-letter.

**Bounded one-shot adapter:** `contracts/vox/notificationOutboxWorker.mjs`, importable into an eventual independently approved existing Core worker. It is not an HTTP route or timer. Disabled by default; injects a **service-role RPC adapter only from a properly controlled Core process**. Validates strict lease and receipt shapes, maintains counters for in-app records only, never claims push/provider send, never retries ambiguous successful network outcomes by overwriting a possible committed DONE. `enabled:true` is merely a code safety flag, never an actual human authorization or evidence of signed deployment.
